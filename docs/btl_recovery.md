# 带宽估计（btl）在弱网卡顿后的快速恢复原理

场景：4 Mbps 链路上每 30s 突发一次 1s 卡顿（带宽降到 400 Kbps）。测试结论：
**btl 全程稳定在 ~497 KB/s（≈ 链路真实容量），卡顿瞬间不下跌，卡顿结束后立即恢复。**

本文解释为什么能"快速恢复"，以及支撑它的几个机制。

---

## 1. 观察到的现象

修复前的表现（作为对比基线）：

```
卡顿(t=50) → btl 从 ~487K 跌到 ~275K → 缓慢爬升 30s → 刚爬到 ~487K → 下一次卡顿 → 再跌
```

即 btl 呈现"爬升-下跌-爬升"的锯齿，平均值远低于链路容量，**永远达不到实际带宽**。

修复后的表现：

```
btl 2~3s 内爬到 ~497K（≈4 Mbps / 8 = 490 KB/s）
此后每次 1s 卡顿：btl 不跌（495~503K 波动），forward 带宽持续 3.3~4.0 Mbps
```

---

## 2. 快速恢复依赖的机制

### 2.1 投递率样本 R 来自接收端实测

- 接收端（node）每报告周期（1s）统计实际收到的字节数 `m_recv_bytes`，
  随 Report 上报给发送端（leaf），作为投递率样本 `R`（bytes/s）。
- R 等于链路的真实瓶颈速率，不受发送端队列、ACK 游标跳缺的影响。
- 小概率随机丢包时按 `R/(1-loss)` 校正（loss 1%~25% 区间），避免把丢包误当容量。

### 2.2 btl 是窗口最大值滤波（max filter）

```cpp
static constexpr std::size_t kWindowSize = 5;   // BtlBw max-filter 窗口
// on_delivery_rate(): 探测片样本入窗，取最大值
m_window[m_window_pos] = R;                      // 只接受探测片(pos<8)的样本
m_btl_bw = max(m_window[0..4]);
```

**这是"快速恢复"最核心的一条**，但要区分两种场景：

- **短暂卡顿（1~2 个低样本，卡顿后恢复）**：一次 1s 卡顿只产生 1~2 个
  低样本（R ≈ 400 Kbps / 8 = 50 KB/s），窗口里其余 3~4 个样本仍是卡顿前
  的 ~490 KB/s 高样本。`btl = max(窗口)` → 低样本被高样本"盖住"，**btl
  不会下跌**，卡顿结束后无需恢复。低样本 5 个探测样本后自然移出窗口。
- **真实持续降带宽（低样本持续涌入）**：若链路带宽长期下降（如视频场景
  4 Mbps → 1 Mbps），低样本会**逐槽替换**高样本。max filter 在窗口被 5 个
  低样本占满前（≈5 个探测样本，若跨排空片可能 ~10s+）**一直保持旧值**，
  期间发送速率仍按 1.25×旧 btl 超发，新链路容纳不下 → 队列堆积、RTT 抬升、
  到达 proxy 队列上限后被丢弃（由 FEC/重传兜底）。**这 5 秒对真实拥塞而言
  就是卡顿本身，跟跌延迟是 max filter 的固有代价**（BBR 的 BtlBw 同理）。
  窗口特意取 5（短窗口）正是为了把这个跟跌延迟压到最小。

### 2.3 探测增益 1.25：让链路成为瓶颈

```cpp
static constexpr double kGainUp = 1.25;    // 探测片
static constexpr double kGainDown = 0.75;  // 排空片（仅探测片建过队列时生效）
// 速率 = btl × gain，app 按此速率发送（--send-adaptive）
```

探测片发送速率 = 1.25 × btl，**刻意高于当前估计**：

- 当 btl < 链路容量/1.25 时：发送速率 1.25×btl 仍低于链路 → 不会拥塞 →
  R = 发送速率 = 1.25×btl → 窗口 max = 1.25×btl → btl 被抬高。
- 当 btl ≈ 链路容量时：发送速率 1.25×btl 超过链路 → 链路成为瓶颈 →
  R = 链路容量 → btl 收敛并锁定在链路真实容量（~490 KB/s）。

即"探测"通过主动超发来探明链路的真实上限；R 样本始终反映"实际能跑多快"。

### 2.4 指数式爬升：1.25×/探测样本

若 btl 因更长的卡顿真的跌到 B，恢复是**指数级**的：

```
B → 1.25B → 1.25²B → 1.25³B → ... 直到 ≥ 链路容量/1.25
```

示例（卡顿后 btl=250K）：

```
250K → 312K → 391K → 488K → (≈链路容量 490K，锁定)
```

每个探测样本（1s）翻 1.25 倍，**3 个样本即从 250K 回到 ~488K**，第 4 个
样本被链路容量钳住——这就是"2~3 秒恢复"的来源。8s 探测片 + 余量足够完成
完整恢复。

### 2.5 排空片不参与 btl 更新

```cpp
if (pos >= kProbePeriods) { recompute_gain(); return; }   // 排空片样本被拒
```

排空片（gain=0.75）的 R ≈ 0.75×btl，若写入窗口会永久压低 max filter。
代码直接拒绝排空片样本，保证 btl 只由探测片的真实容量样本驱动。

### 2.6 三个配套修复（保证上述机制生效）

| 修复 | 作用 |
|------|------|
| **proxy 积压重排**（带宽变化时按新旧速率比压缩已排队报文的 due 时间） | 卡顿结束后积压在 1~2s 内冲刷完，R 立即回到链路容量，不残留 20s+ 的"旧速率尾巴" |
| **pacer 令牌桶 cap 随速率缩放**（`max(mtu×4, pace×20ms)`） | Windows 上 10ms 节拍实际 ~15.6ms，旧固定 cap 5400B≈3 包/拍把线速钳在 ~255KB/s（低于 4 Mbps 链路），R 永远到不了 490K；cap 放大后每拍能发出整个节拍的额度 |
| **app 按估算带宽发送**（`--send-adaptive`） | 需求 = btl×gain，探测片需求 > 链路 → 链路成为瓶颈而非 app 上限；否则固定速率 app（~260KB/s wire）自己就是瓶颈 |

## 3. 为什么 1s 卡顿对 btl 基本无感（数值推演）

1. t=0：btl=497K，探测片发送 1.25×497≈621 KB/s > 链路 490 KB/s。
2. 卡顿 1s：链路降为 400 Kbps，R 样本 = 50 KB/s（1 个低样本入窗）。
3. 恢复：proxy 积压按 10× 压缩，~2s 内冲刷完；R 回到 490 KB/s。
4. 窗口状态（5 槽）：`[490, 490, 490, 50, 490]` → max = 490K → btl 不变。
5. 5 个探测样本后低样本被挤掉：`[490, 490, 490, 490, 490]`。

**注意区分**：上述"免疫"只适用于**短暂卡顿后链路恢复**的情况。若链路真实
带宽长期下降（如看视频时网络从 4 Mbps 掉到 1 Mbps 不再恢复），低样本会
持续入窗：

```
[490, 490, 490, 490, 122] → max=490K（第 1 秒，仍在超发）
[490, 490, 490, 122, 122] → max=490K（第 2 秒）
[490, 490, 122, 122, 122] → max=490K（第 3 秒）
[490, 122, 122, 122, 122] → max=490K（第 4 秒）
[122, 122, 122, 122, 122] → max=122K（第 5 秒，终于跟跌）
```

这 5 秒内发送速率仍为 1.25×490K=612 KB/s > 新链路 122 KB/s → 队列堆积、
RTT 抬升、丢包（FEC/重传兜底）。对真实拥塞，**跟跌延迟 ≈ 5 个探测样本
（5s，跨排空片时更长）**，这正是 max filter 的固有代价；当前实现的补偿
手段是"短窗口"（kWindowSize=5）。

---

## 4. 局限性

- **真实持续降带宽时的跟跌延迟**：max filter 在窗口被低样本占满前（≈5 个
  探测样本，跨排空片时可能 10s+）保持旧 btl，期间超发造成队列堆积/RTT
  抬升/丢包。对"看视频时网络变差"这类真实降速，这 5 秒就是实际卡顿，
  属于当前实现的固有代价。可选的改进方向：引入"持续拥塞跟跌"——当连续
  N 个探测样本显著低于 btl 且 pacer 受限（真实拥塞而非应用受限）时，直接
  把 btl 收敛到低样本值，而不是等窗口自然占满（当前未实现）。
- **探测片样本粒度 1s**：卡顿若落在排空片内，其低样本本就不入窗（2.5），
  跟跌会再延迟最多 8s；落在探测片内则产生低样本，跟跌从下一探测样本开始。
- **app 配额取整**：app 每 5ms 拍按 `floor(estBw×5ms/msgSize)` 发送，实际
  需求略低于理论 pace，恢复曲线略慢于理论 1.25×/样本（实测 380→404→442）。
- **排空片窗口**（kDrainPeriods=8）期间 btl 不更新也不下降，恢复主要发生在
  探测片内；总周期 16s 中探测片占 8s，保证每 16s 至少有一次完整的探测机会。

---

## 5. 一句话总结

**btl 用 5 槽最大值滤波吸收短暂卡顿的瞬时低样本（1s 卡顿无感），用 1.25×
探测增益在需求超链路时把"实际可达速率"采进窗口，因此短暂卡顿期间 btl
不跌、跌了也能在 1 个探测片内按指数曲线快速爬回链路真实容量；而 proxy
积压重排、pacer 桶上限和 app 自适应发送保证 R 样本确实能触达链路真实容量。
代价：对真实持续降带宽（如视频场景），max filter 会延迟跟跌约 5 个探测
样本，期间超发堆积队列——这是"短卡顿免疫"与"快速跟跌"之间当前的取舍。**
