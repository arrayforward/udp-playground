## 6. QSV 编码器稳定性专题（卡顿根因）

### 现象
L4S 场景多次运行出现 10-40s 视频断流（vFrames 停滞、播放端 rx=0），nokey 丢帧 20-50 帧。

### 根因链（已定位并修复）
```
CE 急降（×0.45/×0.30）→ btl/码率大幅跳变 → 编码器重启（QSV 子进程）
+ 播放端 req-keyframe（断流期每 500ms）→ 编码线程 force_idr 重启【无冷却】
+ 编码器崩溃后 respawn（alive 检查）【无冷却】
→ 60s 内 27-36 次重启 → QSV 设备失败（device failed -17）→ 重启风暴
→ 编码器零产出 10-40s → 播放端断流
```

### 修复
1. **统一 4s 重启冷却**（main 循环码率重启 + 编码线程 force_idr + respawn 三路径共享 `last_reset`——冷却期内 IDR 请求合并忽略）
2. **-17 后长退避**（3 连败后退避 2s→30s——设备故障期停止徒劳重启）
3. **统一柔表**（CE 也柔降——btl/码率小步变化——重启诱因减少）

### 修复后
- 重启次数：27-36 → **10-14 次**（与无 CE 网络相当）
- 断流：**消除**（v3 双场景全程无 rx=0）
- 残余：重启次数有随机波动（设备状态）——**QSV 设备 -17 是硬件/驱动层面限制**，冷却与退避已把风险降到最低，偶发一次重启（300ms）可由播放端等 IDR 吸收（丢 8 帧级）

## 8. 结论

1. **两模式均达标**：零排空/贷款循环、音频零欠载、全程无断流——v1-v3 迭代的拥塞控制机制全部落地。

2. **统一柔表（共享表）**：CE/late/loss 共用 0.90/0.75/0.65/0.50——L4S 场景编码器重启从 36 次降到 14 次、断流消除；代价是 CE 收敛略慢（多次小降），但换来 btl/码率渐变（编码器稳定）。

3. **有 L4S vs 无 L4S**：
   - 无 L4S：drop 1、wrote 1340（74% 帧率）——late 保守收敛 2-4.8M，链路利用率低但最稳
   - 有 L4S：drop 20（启动期 12 + 编码器重启期 8）、wrote 1202（67% 帧率）——CE 让收敛值更高（10M 段 13.2M vs 3.1M），利用率高；丢帧差来自起步校准随机性 + 编码器重启偶发
   - **L4S 的价值**：CE 是唯一不依赖发送端状态的客观链路信号（proxy 直测队列），网络支持时应启用（利用率高）；无 CE 网络靠 late 同样收敛（保守但稳）

4. **QSV 编码器稳定性**（接受现状）：-17 设备失败是硬件/驱动层面限制——冷却（4s 共享）+ 长退避（30s）+ 柔降（重启诱因减少）已把风险降到最低；偶发一次重启（300ms + 等 IDR）造成个位数丢帧，可接受。

5. **已知残余**：
   - 恢复段爬升受 recv×1.2 约束慢（60s 内收敛 3-6M，长时间恢复可继续爬）
   - L4S 启动期（车库段报告丢失 20%）起步校准随机（报告未丢则 4.9s 降、丢了则延迟）——可考虑起步码率上限时间延长
   - lite 单线程：音频可行、高码率视频不可行（接收侧 RS 解码拖慢 recvfrom）

6. **下一步建议**：
   - 恢复段爬升约束放宽（recv×1.2 仅 fast 排空后生效）
   - L4S 起步校准强化（车库段报告丢失时用 probe 校准兜底——已实现 set_seed_and_clamp，可验证）
   - QSV 稳定性：驱动升级 / 720p 验证 / 编码器守护（长退避后通知应用）

## 9. lite 模式音频播放终端资源占用（附加测量）

- 测试：`--video-off`（音频-only）+ 两端 lite 单线程 + 驾驶场景，60s
- 记录：`test-results/lite-audio-res2/`（每 1s 采样 proc.csv）
- 平台：Intel Core Ultra 5 125H（14 核/18 线程，单 P 核 ~4.5GHz × 4 DMIPS/MHz ≈ 18,000 DMIPS = 18 kDMIPS）

### 9.1 内存占用（video-player 进程）

| 阶段 | 工作集 WS | 私有内存 |
| --- | --- | --- |
| 启动（0-5s） | 13,580 → 14,120 KB（13.3-13.8MB） | 2,812 → 3,076 KB（2.7-3.0MB） |
| 连接/握手（5-10s） | 14,120 KB 稳定 | 3,076 KB |
| 稳态播放（10-55s） | 14,120 → 14,348 KB（**14.0MB 稳定**） | 3,212 → 3,284 KB（**3.2MB**） |
| 峰值（60s） | 14,348 KB | 3,284 KB |

ffplay 子进程（视频解码器，音频-only 时空闲）：WS 84,444 KB、私有 105,724 KB——大头在 ffplay（SDL+ffmpeg 库加载），音频-only 终端可不启动省 ~100MB。

### 9.2 CPU 占用（60s 累计 1.047s）

| 阶段 | CPU% | kDMIPS（单核基准 ×18） |
| --- | --- | --- |
| 启动（0-5s） | ~3.8% | ~0.68 |
| 稳态播放（10-55s） | **~1.5%** | **~0.27** |
| 全程平均 | 1.75% | ~0.31 |

### 9.3 结论

- **lite 音频终端极轻**：稳态 14MB 工作集 / 3.2MB 私有 / 1.5% 单核 CPU（~0.27 kDMIPS）
- 内存 0-60s 仅 +0.2MB（无泄漏趋势）
- 对比：lite 高码率视频不可行（RS 解码拖慢接收 → UDP 丢包 drop 242）；音频-only 完全可用（underrun 0、全程连续）
