# 驾驶场景 L4S 对比测试报告（详细分析版）

- 日期：2026-08-19
- 场景：`scenarios/video_driving_l4s.txt`（有 L4S）vs `scenarios/video_driving_nol4s.txt`（无 L4S）
- 测试记录：`test-results/driving-l4s-final2/`、`test-results/driving-nol4s-final/`
- 发送端/播放端：video-sender / video-player（4 线程模式），报告周期 333ms，迟到线 = P50 + F/btl + 16ms
- 两场景除 L4S 开关外参数完全一致（渐变版，2s/档，60s）

---

## 1. 测试环境与方法

| 项 | 配置 |
| --- | --- |
| 链路 | 本地环回 + udp-proxy 场景限速（bps 精确、每 2s 渐变） |

## 3. btl 轨迹逐段分析（B/s，×8 = bps）

### 3.1 无 L4S（driving-nol4s-final）

```
车库段:   3750000 →(probe 校准) 98731(3.1s) → 148096 → 241484 → 362226(7.4s)
         → 271669(8.8s 轻降) → 407503(9.6s)
人群段:   458440(10.6s 稳定 3.7M) → 297986(13.8s) → 193690(15.8s) → 197181→295771(19-20s)
正常段:   443656(21.4s 爬升) → 332742(24.2s) → 359624(25-28s 稳定) → 539436(29.2s 爬升)
郊区段:   539436(30-34s 稳定 4.3M≈4M 链路) → 350633(35.3s late 降) → 315569(39.8s)
恢复段:   315569(40.5s) → 205119(41.6s) → 461517(44.8s 爬) → 269987(46.8s 降)
         → 607470(50.3s 爬) → 394855(52-56s 稳定) → 433462(57-59s)
```

**逐段解读**：
- **车库段（0-10s）**：起步 30M 种子 → 握手 probe 测速（3.1s 到达）→ `set_seed_and_clamp` 将 btl 钳到实测（98731 B/s = 790Kbps——弱网握手期 probe 测偏，仅作保守起步）→ 恢复台阶 ×1.5 爬升（148K→241K→362K→407K）。8.8s 一次 ×0.65 轻降（late 0.1+ 档）——车库段长尾延迟（80-200ms）个别帧迟到，柔表温和响应。**收敛 3.3M（407K×8），低于 5M 链路**——late 信号滞后 + 爬升受 recv 约束，未贴满链路（保守但稳定）。
- **人群段（10-20s，10M 链路）**：10.6s 稳定 458440（3.7M，远低于 10M——不超发，late 无信号）。13.8s 起两次缓降（297986、193690）——P50 升至 28ms（播放端帧慢——令牌 1.5M 视频下限附近拖帧），late 缓降 ×0.65/×0.75。**最终 1.5-2.4M（码率下限附近）**——该段未充分利用 10M（因起步偏低 + 缓降保守），但零丢帧、零欠载。
- **正常段（20-30s，30M 链路）**：爬升（443K）→ 微降（332K——FEC 探测超发触发 late）→ 稳定 359K（2.9M）→ 29.2s 539K（爬升）。**爬升慢的根因**：恢复台阶 ×1.5 受 `recv_rate×1.2` 约束（recv_rate ≈ 当前发送速率，形成 1.2×/报告 的慢爬），20s 内只从 3M 爬到 4.3M。
- **郊区段（30-40s，4M 链路）**：539K（4.3M）≈ 4M 链路边缘轻微超发 → 35.3s late 缓降 ×0.65（350K=2.8M）→ 315K 稳定。**收敛在 4M 链路下方**（2.5M）——late 是播放端统计（滞后），链路收紧后约 3-5s 才反映。
- **恢复段（40-60s，30M 链路）**：41.6s 205K（追赶期 late——郊区段欠账）→ 44.8s 461K（爬）→ 46.8s 270K（微降）→ 50.3s 607K（爬）→ 52-59s 394-433K 稳定。**无崩底、无排空、无贷款循环**——追赶期缓降 + 爬升交替，收敛 3.2-4.8M。

### 3.2 有 L4S（driving-l4s-final2）

```
车库段:   3750000 →(报告超时 ×0.5) 1875000(4.9s) → 1218750(7.7s 柔表降) → 稳定 1218750
人群段:   914062(12.2s CE 降) → 594140(13.8s CE 降) → 稳定 594140(16-21s)
正常段:   386191(23.2s) → 418694(28.6s) → 628041(30.0s 爬升)
郊区段:   628041(30-35s 稳定 5M≈4M 略超) → 408226(36.3s CE 降) → 稳定 408226
恢复段:   408226(40.2s) → 265346(41.6s) → 238811→214929(44-47s 缓降) → 483589(48.9s 爬)
         → 稳定 483589(49-56s) → 725383(57.2s 爬升)
```

**逐段解读**：
- **车库段（0-10s）**：报告丢失 20% → `check_report_timeouts` 触发 ×0.5（30M→15M，4.9s）——这是**报告超时降速**（非拥塞判定），one-shot（m_report_stall 防重复）。7.7s 一次柔表缓降（late 主导，×0.65→1218750=9.75M）——**收敛 9.75M > 5M 链路**（略超但稳定——late 未持续超线）。**与无 L4S 对比**：无 L4S 靠 probe 钳制起步（790K），有 L4S 靠报告超时（15M）——有 L4S 起步偏高，之后靠 late 缓降。
- **人群段（10-20s，10M + L4S）**：**CE 驱动两次降速**（12.2s ×0.45→914K、13.8s ×0.65→594K）——CE 是 proxy 直测队列积压（发送 9.75M > 10M 链路？——不超——**CE 来自 10s 场景切换的积压尾流 + 关键帧突刺**）→ 收敛 594K（4.75M）。**CE 响应比无 L4S 的 late 响应更快**（CE 在发送端立即生效，late 要等播放端统计 + 报告往返）。
- **正常段（20-30s，30M）**：23.2s 386K（20s 场景切换 CE 尾流缓降）→ 28.6s 418K → 30.0s 628K（爬升）。
- **郊区段（30-40s，4M + L4S）**：628K（5M）稳定到 35s（≈4M 链路略超，CE 阈值 20ms 未持续触达）→ 36.3s CE 降 ×0.65（408K=3.3M）→ 稳定。**收敛 3.3M**。
- **恢复段（40-60s，前 12s L4S + 渐变）**：40-47s 缓降（265K→215K——前 12s 仍 l4s on + 渐变段 CE/late 响应，追赶期）→ 48.9s 483K（爬升）→ 49-56s 稳定 → 57.2s 725K（爬升）。**无崩底、无排空、无贷款循环**。

### 3.3 轨迹对比小结

| 段 | 无 L4S 收敛 | 有 L4S 收敛 | 差异原因 |
| --- | --- | --- | --- |
| 车库（5M） | 3.3M | 9.75M→缓降 | L4S 起步靠报告超时（15M 起），无 L4S 靠 probe 钳制（0.8M 起）；两者都未贴满 5M（late 保守） |
| 人群（10M） | 1.5-3.7M | 4.75M | L4S CE 快速收敛；无 L4S late 滞后 + 播放端帧慢缓降更深 |
| 正常（30M） | 2.9-4.3M | 3.1-5M | 都受 recv 约束慢爬，L4S 略高（CE 消失后爬升快一步） |
| 郊区（4M） | 2.5-4.3M | 3.3-5M | 都收敛在 4M 附近，轻微超发由 CE/late 各自修正 |
| 恢复（30M） | 3.2-4.8M | 1.7-5.8M | 都稳定爬升-缓降交替，无崩底；L4S 波动略大（前 12s 仍 L4S 开） |

**核心观察**：两种模式都**无崩底、无排空、无贷款循环**——上一代版本的"恢复段反复降 + 贷款死锁"已彻底消除。L4S 的 CE 响应更快更准，但收敛值略高（依赖 CE 阈值触达）；无 L4S 的 late 更保守（收敛偏低但更稳）。

### 差异根因分析

| 差异 | 原因 |
| --- | --- |
| L4S 0-20s 停等关键帧 | **QSV 编码器侧偶发**（非拥塞控制）：播放端丢帧缺口 → 每 500ms 发 req-keyframe 命令 → 发送端 force_keyframe 重启编码器（300ms 出 IDR）——本次运行中重启未及时产出（两次运行时段不同：0-30s / 10-20s，随机）——链路/协议机制正常（btl 收敛、音频无损、无 evac/loan） |

| wrote 差异（871 vs 1279） | 断流 10s 损失 + 之后收敛码率略低 |

## 5. 信号链与机制行为分析

### 5.1 无 L4S：late/delay 单链

```
播放端: 帧延迟 D（首片→重组完成）→ 迟到线 = P50 + F/btl + 16ms → late_ratio
发送端: congested = (late>2%) || (delay_ewma>20ms) || (loss>2%)
        降速 = 柔表（late 主导）：×0.90/×0.75/×0.65/×0.50（1%/5%/20%/50% 档）
```

行为特征（实测）：
- **起步**：probe 校准钳制（790K）→ 爬升——**无超发风险**（起点低于链路）
- **收敛**：late 信号滞后 1-2 个报告（播放端统计+往返）→ 缓降温和（×0.65/0.75）→ 收敛值偏低（保守）
- **恢复**：爬升受 recv×1.2 约束——慢但稳（无跳帧后爬满格超发问题，因为本场景无跳帧）
- **优点**：零 evac/loan、零丢帧、零断流
- **代价**：链路利用率低（3-4M vs 链路 5-30M）——**画面清晰度保守**

### 5.2 有 L4S：CE + late 双链

```
proxy:  队列积压 backlog（纯带宽 bw_drain）> 20ms → CE 报文（4B magic 直发播放端）
播放端: CE 报文计数 → ce_ratio（样本 ≥20 才判）→ 报告带出
发送端: congested = (ce>1%) || (late>2%) || ...
        降速 = CE 主导急表（×0.65/×0.45/×0.30/×0.20）；late 主导柔表
```

行为特征（实测）：
- **CE 响应更快**：proxy 直测积压（不依赖播放端统计）→ 报告到达即降（人群段 12.2s/13.8s 两次）
- **CE 误触发防护**（本次迭代全部落地）：
  - `bw_drain` 纯带宽积压：delay-normal 正常延迟不触发 CE（修复前 40-52s 渐变段 CE 误判反复降的根源）
  - CE 最小样本门槛（<20 报文不判）：发送受限/暂停期 CE 尾流小分母虚高被过滤
  - 关键帧超发并入冻结期：IDR 60KB 传输 27-33ms 触达 l4s 阈值的突刺 CE 被豁免
  - overload EWMA：IDR 突刺的报告窗口错位不再误判持续超发
- **实测 CE 事件**：proxy reverse l4s=3687（队列积压超阈值事件数——CE 判定活跃工作）
- **优点**：CE 真实超发时急降快收敛（郊区段 4M 收敛 3.3M）
- **代价**：CE 阈值 20ms 触达边缘（轻微超发 5M vs 4M 链路）时 CE 持续 → 降速略频繁

### 5.3 关键机制逐项验证（轨迹证据）

| 机制 | 证据（实测） |
| --- | --- |
| 时钟校准 max-filter | 两场景 P50 正常反映（4-60ms），无恒 4ms 失真——迟到线可信 |
| probe 起步校准 | nol4s 3.1s 98731（钳制起步）；l4s 无钳制（报告超时 ×0.5 起步） |
| 柔表（late 主导） | 两场景降速多为 ×0.65/×0.75（late 档）——无急降崩底 |
| 急表（CE 主导） | l4s 人群/郊区段 CE 降 ×0.45/×0.65——真实超发快速收敛 |
| 双模式排空 | 两场景 0 次 evac/loan——强降信号未出现（柔表 + CE 修复后无需跳帧） |
| 报告超时 ×0.5 | l4s 车库段 4.9s 1875000（=30M×0.5，报告丢失 20% 触发，one-shot） |
| recv 约束爬升 | 恢复段慢爬（1.2×/报告）——稳定不崩，60s 内收敛 3-6M |
| 破产清算 | 无触发（排空未发生）——作为兜底待命 |

## 7. 结论

1. **两模式均达标**：零排空、零贷款循环、音频零欠载——上一代"恢复段反复降 + 贷款死锁 + 令牌断流"问题彻底消除。

2. **无 L4S（纯 late/delay）**：drop 1、underrun 0、全程连续播放——**稳定优先**。代价是收敛偏低（3-4M vs 链路 5-30M），画面清晰度保守。适用：无 ECN 支持的网络。

3. **有 L4S（CE + late）**：underrun 0、零循环、CE 快速收敛（郊区 4M 收敛 3.3M）——**响应优先**。残余 drop 19 来自 0-20s QSV 编码器偶发停等关键帧（非链路机制）；CE 误触发三类根源（delay 污染/小样本/IDR 突刺）已全部修复（proxy l4s 事件 3687 为真实积压）。

4. **L4S 的价值定位**：CE 是唯一"不依赖发送端状态"的客观链路信号（proxy 直测队列）——让发送端在"排队未丢包"阶段提前降速；无 CE 网络靠 late（时钟校准后真实）+ 柔表同样收敛，只是更保守。

5. **已知残余**：
   - 恢复段爬升受 recv×1.2 约束慢（60s 内收敛 3-6M，长时间恢复可继续爬）
   - L4S 场景 QSV 偶发停等关键帧（编码器侧，待跟进）
   - lite 单线程：音频可行、高码率视频不可行（接收侧 RS 解码拖慢 recvfrom）

6. **下一步建议**：
   - 恢复段爬升约束放宽（recv×1.2 → 仅 fast 排空后 N 报告生效，非排空期正常 ×1.5）
   - QSV 停等关键帧排查（force_keyframe 可靠性）
   - 无 L4S 场景链路利用率提升（late 阈值/柔表微调，收敛向链路靠近）
